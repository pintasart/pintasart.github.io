Agruras de automatizar a publicação da minha página

Spoiler: no fim funciona. Mas entre o “vou só meter isto no GitHub Actions” e o primeiro deploy feliz, passei por mais plot twists do que numa novela das nove.

Acto I — “Isto é só um script”

Tenho um site em Pelican. Gera HTML bonitinho, o make publish faz o que tem a fazer, e eu pensava que o pior já tinha passado quando o Pelican deixou de reclamar dos plugins. Engano. O universo guardou os boss fights para a fase CI/CD.

A primeira humildade foi humilde mesmo: links no menu que apontavam para /sobremim/ quando o Pelican, educadamente, tinha gerado /sobre-mim/. O Pelican não discute contigo — faz slugify e pronto. Eu é que estava a mandar o browser para uma página que tecnicamente só existia na minha cabeça. Clica, 404, drama existencial.

Moral do acto: o URL real é o que o build gera, não o que parece bonito no menu. Olhar para a pasta output/ poupa terapia.

Acto II — Repositórios, identidades e crises de visibilidade

Depois veio a questão existencial: repo público vs privado e o GitHub Pages a fazer lembranças de que nem tudo combina com tudo. Quis publicar o source privado e o site noutro sítio — normal. Só que cada escolha vem com regras: tokens, branches, permissões, e aquela sensação de que estás a negociar um contrato com o próprio Git.

Apaguei o pintasart.github.io antigo e quis reencaminhar a vida. Claro. É como mudar de casa e achar que os móveis sabem onde vão parar sozinhos.

Acto III — O token que não era token

Entrei no peaceiris/actions-gh-pages com confiança de quem já leu meia documentação.

Primeira ronda: GITHUB_TOKEN no repo de origem a tentar empurrar para outro repo. O GitHub olha para ti com aquele olhar de “nice try” e devolve 403. Não é pessoal — é política. O token da workflow não é teu carteiro para empurrar código para vizinhos sem autorização.

Segunda ronda: “not found deploy key or tokens”. Isto é o equivalente a chegares à porta e perceberes que te esqueceste da chave e do telemóvel e do backup da chave. Ou seja: o action correu, mas o personal_token chegou vazio. Clássico: o workflow a pedir DEPLOY_TOKEN_MY_WEBPAGE e o secret no GitHub a chamar-se DEPLOY_TOKEN — ou o contrário. O YAML não faz telepatia; se o nome não bater certinho, o GitHub injecta nada e o peaceiris fica ofendido.

Terceira ronda: PAT com nome bonito mas sem scopes para escrever no destino. Outro 403, desta vez com aroma a “autenticaste-te mas não tens caneta para assinar aqui”.

Acto IV — Epifania com cheiro a café

A solução, quando calha, é quase aborrecida de simples:

  1. Gerar um PAT (classic com repo, ou fine-grained com Contents: write no pintasart/pintasart.github.io).
  2. Guardar no repo fonte (pintasart.github.io-src) como secret — o nome que o workflow espera (DEPLOY_TOKEN ou o que lá estiver no personal_token:).
  3. No repo destino, garantir que o site está configurado para servir a branch certa (no teu caso, main com o conteúdo publicado).
  4. Push em main → build → deploy → ir ver se o site respirou.

Se quiseres evitar PAT, há o caminho da deploy key (SSH) no repo destino — mais trabalho inicial, menos “renovar token daqui a X meses”.

Resumo executivo (para o teu eu do futuro)

  • Cross-repo deploy = precisas de credencial tua (PAT ou deploy key), não só do GITHUB_TOKEN do workflow.
  • Secrets com nomes errados = token invisível = erro “not found deploy key or tokens”.
  • 403 = token existe mas não manda no repo destino (scopes, SSO, branch protection, ou repo que nem existe).
  • URLs no menu = conferem com o que sai em output/; o Pelican é o juiz.

E pronto. Automatizei. Ri. Chorei. Voltei a rir. Agora escrevo isto para que, da próxima vez, o erro seja novo — porque repetir o mesmo 403 já não tem piada nenhuma.

Até à próxima agrura.
